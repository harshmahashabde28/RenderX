How to use this book
This book is both a project history and a study guide. Read Chapters 1 to 4 to understand why the
project exists and how the renderer calculates a screen point. Read Chapters 5 to 8 to understand the
Learning Laboratory features and how to demonstrate them. Use the appendices when you need a
file-by-file walkthrough, exact controls or viva practice.
The source code is the authority. The original planning documents describe intentions from before
implementation. Where the final implementation is smaller or different, this book labels the
difference instead of treating the plan as proof.

1. Why RenderX was built
The starting problem
A 3D graphics pipeline is often taught as a list of formulas. Students may remember a rotation matrix or
perspective equation without seeing how those operations combine in a program. RenderX started with
a simple teaching goal: display a small wireframe, let a student manipulate it, and keep every
calculation readable enough to explain in a viva.
The design deliberately uses Python, Pygame and the standard library. Pygame provides the window,
keyboard and mouse events, fonts and two-dimensional lines. The project code performs the
three-dimensional work directly. This makes the boundary visible: RenderX calculates points; Pygame
draws the resulting lines.
Constraints that shaped the design
• Keep the existing project architecture and working controls.
• Do not use OpenGL, NumPy, Blender, Unity, Unreal or another 3D engine.
• Use explicit operations that a beginner can trace in a debugger.
• Keep the application offline and dependency-light.
• Protect the original mesh data so repeated interaction never permanently distorts it.
• Use tests for mathematics and safety, then use screenshots for visual checks.
Before code: college milestones and the documentation
baseline
The supplied documentation began as a planning package on 2026-09-12. The Project Hub framed
RenderX as a small offline college demonstration. The PRD described the users and success criteria.
User Flows specified a simple one-screen journey. Technical Design described the data model and
module boundaries. The Roadmap divided implementation into small stages. Testing, Decision Log,
Development Log and Backlog documents recorded evidence and open work. AGENTS.md set the safety
rules for readable maths, preserved geometry and honest verification.
At that point the documents correctly said implementation was pending. They were planning artefacts,
not evidence that code existed. The first archive supplied for audit was the runnable Milestone 3
renderer. The second was the Phase 2 extension. Later Checkpoint 3 archives added the Learning
Laboratory. College notes remain outside the application repository for Obsidian-style tracking, while
README.md travels with the source.
One useful lesson from this project is the difference between a requirement and an implementation.
The early plan proposed a 1000 x 700 layout and a small shape set; the actual first renderer used a
1120 x 740 internal screen and included a rectangular prism. The final source and tests are the
correct reference for what is delivered.

The idea changed after the renderer worked
The early renderer was already useful as a technical demonstration, but it did not expose enough of its
internal state. The project then moved toward the Learning Laboratory identity. The main innovation is
the educational integration: the application displays intermediate values from its own real pipeline,
connects those values to formulas, and gives students controlled experiments and questions. It is an
educational product around a software renderer, rather than a new rendering algorithm.
"If the student can point at a number on screen and explain which line of mathematics
produced it, the renderer has become a laboratory."
What the final product is
The final product is a desktop wireframe laboratory. It supports seven workspaces, a low-poly model
library, an OBJ sample, pipeline snapshots, perspective and orthographic comparison, topology
inspection, guided lessons, a deterministic quiz, clipping and transformation-order experiments, visible
controls and an eight-step presentation path.

Version 1: the first working renderer
The first archive already had a complete small renderer. Mesh data was stored as vertices and indexed
edges. Scene state stored the selected shape, angles, position and scale. The transformation module
applied scale, X rotation, Y rotation, Z rotation and translation. The camera performed guarded

4. The data model: vertices, edges,
faces and state
Mesh
Mesh is a dataclass containing a list of three-number vertex tuples and a list of two-index edges. Final
meshes may also carry polygon faces, a normalization scale and warnings. The constructor validates
finite coordinates, integer edge indices, duplicate edges, self-connections and optional face indices.
Built-in data is validated at startup; malformed data raises a clear error while invalid external OBJ input
is rejected by the loader.
@dataclass
class Mesh:
    vertices: list[tuple[float, float, float]]
    edges: list[tuple[int, int]]
    faces: list | None = None
    normalization_scale: float | None = 1.0
    warnings: list[str] = field(default_factory=list)
Why edges use indices
An edge such as (0, 1) says to connect the first and second entries in the vertex list. This avoids
repeating point coordinates and makes topology explicit. A cube has eight vertex entries and twelve
unique edges. A polygon face is converted into boundary pairs, including the closing pair from its last
vertex back to its first.
Scene
Scene stores the active shape name, three angles, an XYZ position, a uniform scale, projection mode
and axis visibility. Its methods clamp the position and scale to safe limits. Selecting a shape calls reset()
so a newly chosen model starts predictably. Reset restores the default pose while retaining the selected
shape and current projection/axis settings.
LearningState
LearningState stores the current mode, selected vertex, active pipeline stage, comparison guides,
lesson index, answer visibility, clipping depth, Challenge object, demo step and help visibility. It does
not own the mesh or scene pose. This separation lets the same object be inspected in multiple modes.
Immutability by recomputation
The stored model vertices remain the original coordinates. Every frame calls transform_vertex() again
using current scene values. This prevents repeated key presses from accumulating rounding error or
permanently changing the model. The tests explicitly compare original vertex lists before and after
interaction.

5. The 3D mathematics, step by step
Coordinate convention
RenderX uses X to the right, Y upward and positive Z away from the camera. The camera faces positive
Z. Pygame screen Y points downward, so projection subtracts the vertical screen offset from the screen
center. Angles are stored in radians for math functions and displayed in degrees for people.
Scaling
Uniform scaling multiplies every coordinate by one factor s. For p = (x, y, z), scaled(p) = (s*x, s*y, s*z).
For example, scaling (1, 2, 3) by 2 gives (2, 4, 6). Scaling occurs before rotations so the model grows
around its local origin.
Rotation around X
x' = x
y' = y*cos(a) - z*sin(a)
z' = y*sin(a) + z*cos(a)
X stays fixed. The Y and Z coordinates form the rotating pair. At +90 degrees, (0, 1, 0) becomes (0, 0,
1).
Rotation around Y
x' = x*cos(a) + z*sin(a)
y' = y
z' = -x*sin(a) + z*cos(a)
Y stays fixed. At +90 degrees, (0, 0, 1) becomes (1, 0, 0).
Rotation around Z
x' = x*cos(a) - y*sin(a)
y' = x*sin(a) + y*cos(a)
z' = z
Z stays fixed. At +90 degrees, (1, 0, 0) becomes (0, 1, 0).
Translation
After all three rotations, position is added component by component: world = rotated + (tx, ty, tz).
Translating (1, 0, 0) by (2, 3, 4) gives (3, 3, 4). Translation changes where the object is; it does not
change the stored mesh or its shape.
The complete transform order
original -> scale -> rotate X -> rotate Y -> rotate Z -> translate -> world
The order is part of the design. Scale then rotate then translate keeps translation in world coordinates.
If translation is performed first, later rotations rotate the translation vector around the origin. The two
experiments in the Laboratory print both outcomes for the same point and pose.

6. Camera, projection and clipping
Camera-relative coordinates
The camera has a position tuple. To obtain a camera-relative point, RenderX subtracts the camera
position from the world point. The default camera is (0, 0, 0). The camera-relative lesson uses (1, 0, -1)
to make the subtraction visible without changing the global scene.
Perspective projection
screen_x = cx + f*x/z
screen_y = cy - f*y/z
Here (cx, cy) is the screen center and f is focal length. Dividing by z is perspective division: increasing
depth reduces the offset from the center. If depth doubles while x and y stay fixed, the projected offset
halves. RenderX refuses non-finite points and points at or behind the near depth before division.
Orthographic projection
screen_x = cx + k*x
screen_y = cy - k*y
Orthographic projection uses a fixed pixels-per-world-unit scale k. Fully visible geometry keeps the
same apparent size as it moves along Z. It still uses the near plane for safe visibility, so a model
crossing the near plane can lose outline segments.
Near-plane clipping
Projection division becomes unsafe when an endpoint is too close to the camera. RenderX clips each
edge in camera space before projection. If both endpoints are in front of the near plane, keep the full
edge. If both are behind, reject it. If the edge crosses, find the intersection with z = near_z.
t = (near_z - A.z) / (B.z - A.z)
intersection = A + t*(B - A)
I.x = A.x + t*(B.x - A.x)
I.y = A.y + t*(B.y - A.y)
I.z = near_z
For A.z = -0.9, B.z = 1.1 and near_z = 0.1, t = (0.1 + 0.9)/(1.1 + 0.9) = 0.5. The intersection is halfway
along the segment. clip_edge_near() is shared by object edges, axes and the clipping lesson.
Why clipping belongs to edges
A selected vertex can be hidden while an edge connected to it remains partly visible. Therefore
pipeline.py reports whether an individual point has a safe screen coordinate, while
camera.project_edge() and clipping.py decide the visible portion of each segment.

7. From transformed points to a
wireframe
Renderer sequence
renderer.py transforms every stored vertex once for the current frame, asks the camera to project
points for vertex dots, and asks project_edge() for each edge. project_edge() converts world endpoints
to camera space, clips the segment, projects the remaining endpoints and returns a drawable pair. The
viewport clip is temporarily set so lines cannot overwrite the information panel. A screen-space grid is
then drawn behind the model.
world_points = [transform_vertex(p, scene) for p in mesh.vertices]
for start, end in mesh.edges:
    segment = camera.project_edge(world_points[start], world_points[end], mode)
    if segment is not None:
        pygame.draw.line(surface, ACCENT, segment[0], segment[1], 2)
World axes
axes.py draws a red X, green Y and blue Z reference triad from fixed world coordinates beside the
model. The axes are independent of object rotation, use the same camera and clipping path, and accept
a viewport and focal length for Compare Mode. X toggles them.
Selected point marker
The selected point is highlighted after its final screen projection. In Pipeline Mode, the gold marker
remains the final screen location while the panel highlights whichever intermediate stage the student is
reading. If projection is unsafe or outside the viewport, no marker is drawn.
No hidden-surface removal
RenderX is a wireframe teaching renderer. It draws visible projected edges even when they belong to
the rear of an object. This keeps topology easy to see and avoids introducing a depth buffer or lighting
model.

8. OBJ loading and error handling
Supported subset
The loader accepts vertex lines beginning with v and polygon face lines beginning with f. Face entries
may be positive indices alone or include ignored texture and normal suffix syntax: v, v/vt, v//vn or
v/vt/vn. OBJ indices begin at 1, so the loader subtracts one for Python lists. Polygon boundaries are
closed and shared undirected edges are deduplicated.
Normalization
After reading valid geometry, the loader centers its bounding box and scales the longest extent to two
world units. Mesh stores the normalization factor for Mesh Inspector. Large finite inputs are reduced
before bounding-box arithmetic so normalization remains safe.
Failure behavior
• Missing, unreadable, empty, malformed, non-finite or zero-extent files raise a readable error.
• Negative indices, unsupported line records, materials, textures and curves are not interpreted.
• Size limits protect the small offline application: 2 MB, 20,000 vertices and 50,000 unique edges.
• The caller keeps the previously active mesh and pose if loading fails.
• Unsupported commands are recorded as warnings when the rest of the file remains valid.
try:
    mesh = load_obj(path)
except (OSError, ValueError, UnicodeError) as error:
    return f"OBJ load failed: {error}"
models["OBJ house"] = mesh
scene.select("OBJ house")

14. Known limitations and honest
future work
The project is complete within its compact final scope. The limits below are documented so a viva
explanation stays accurate.
• Wireframe rendering only: no filled polygons, lighting, textures, hidden-surface removal or depth
buffer.
• The camera is fixed; there is no free-fly camera or camera control panel.
• The delivered procedural set contains 15 shapes. Icosahedron, hemisphere, capsule, Mobius strip and
additional surfaces remain stretch work.
• Shape parameters are function arguments in shapes.py, not runtime sliders.
• Challenge questions are deterministic multiple-choice questions; there is no free-answer grader or
database.
• Lesson completion, score and demo state are memory-only and reset when the program exits.
• The demo is manually advanced by the presenter rather than timed automatically.
• The dashboard scales proportionally but does not reflow into a different mobile layout.
• OBJ support intentionally excludes negative indices, materials, textures, curves and standalone line
records.
• Physical Windows controls, target-laptop performance and long-duration stability still require the user
to verify them locally.
Why leaving these out was sensible
Each omitted feature would introduce a new subsystem or a new mathematical concern. Filled
rendering would require polygon rasterization and visibility rules. Textured OBJ would require material
and image handling. Sliders and persistence would expand state management. The final project keeps
the central teaching path stable: manipulate a model, inspect the pipeline, compare views, experiment,
answer and demonstrate.

Appendix C. Viva questions and model
answers
These questions are arranged from simple project understanding to implementation detail. Use the
short answers first, then expand them with the chapter references when your professor asks a
follow-up.
1. What is RenderX?
Answer: It is an offline Python and Pygame software wireframe renderer that calculates a 3D graphics pipeline
explicitly and displays the result as 2D lines.
2. Why did you choose Pygame?
Answer: Pygame supplies the window, events, fonts and 2D drawing while leaving the 3D mathematics visible
in our own Python code.
3. Did you use OpenGL or NumPy?
Answer: No. The project uses Python, Pygame and the standard library only.
4. What is a wireframe?
Answer: A wireframe represents a model with vertices and edges, so the structure is visible without filled faces
or lighting.
5. What is a vertex?
Answer: A vertex is a point stored as an x, y, z coordinate tuple.
6. What is an edge?
Answer: An edge is a pair of integer indices that connects two vertices.
7. Why store edge indices instead of repeated points?
Answer: Indices avoid duplicate coordinate storage and make topology explicit and easy to validate.
8. How many vertices and edges does the cube have?
Answer: Eight vertices and twelve unique edges.
9. What does Mesh validation check?
Answer: Finite three-coordinate vertices, integer in-range edge indices, duplicate or self edges and optional
face indices.
10. What is the role of Scene?
Answer: Scene stores the active model name, orientation, position, scale, projection choice and axis visibility.
11. Why are original vertices never mutated?
Answer: The renderer recomputes every frame from the original mesh, preventing accumulated distortion after
repeated transformations.
12. What is the transform order?
Answer: Scale, rotate around X, rotate around Y, rotate around Z, then translate.
13. Why does transform order matter?
Answer: Operations generally do not commute. Translating before rotation rotates the translation vector
around the origin.
14. State the X rotation formula.
Answer: x'=x, y'=y*cos(a)-z*sin(a), z'=y*sin(a)+z*cos(a).
15. State the Y rotation formula.
Answer: x'=x*cos(a)+z*sin(a), y'=y, z'=-x*sin(a)+z*cos(a).

36
16. State the Z rotation formula.
Answer: x'=x*cos(a)-y*sin(a), y'=x*sin(a)+y*cos(a), z'=z.
17. Why are angles stored in radians?
Answer: Python math.sin and math.cos use radians; the UI converts them to degrees for readable display.
18. What does translation do?
Answer: It adds the scene position to the rotated point and changes location without changing shape.
19. What are camera-relative coordinates?
Answer: They are world coordinates minus the camera position.
20. What is perspective projection?
Answer: It maps x and y using focal length divided by positive camera depth, making distant points appear
closer to the screen center.
21. Give the perspective formula.
Answer: screen_x = cx + f*x/z and screen_y = cy - f*y/z.
22. Why is there a minus sign in screen_y?
Answer: World Y increases upward but Pygame screen Y increases downward.
23. What is orthographic projection?
Answer: It multiplies x and y by a fixed scale without dividing by depth, so fully visible size is independent of
distance.
24. What changes when P is pressed?
Answer: The projection mode changes while the current scene pose remains unchanged.
25. Why is near-plane clipping necessary?
Answer: It prevents unsafe perspective division and preserves the visible portion of an edge that crosses the
near plane.
26. What happens if both edge endpoints are behind the near plane?
Answer: The edge is rejected and nothing is drawn.
27. What happens if one endpoint is behind?
Answer: The crossing point is calculated and the visible part is drawn from the intersection to the front
endpoint.
28. State the interpolation equation.
Answer: t = (near_z - A.z)/(B.z - A.z), then I = A + t*(B - A).
29. Why is clipping done before projection?
Answer: Projection divides by depth, so the segment must be made safe in camera space before that division.
30. Why can a hidden selected point still belong to a visible edge?
Answer: Point visibility and segment visibility are different; an edge can cross the near plane and retain a
partial section.
31. How are axes drawn?
Answer: A fixed world-aligned triad is projected through the same camera and clipping functions as object
edges.
32. What OBJ syntax is supported?
Answer: v positions and positive-index polygonal f faces, including optional texture/normal suffix syntax that is
ignored.
33. How are OBJ indices converted?
Answer: OBJ index 3 becomes Python index 2 because OBJ starts counting at one.

A compact two-minute speaking script
RenderX is a software 3D wireframe renderer built from scratch with Python and Pygame. I begin with a
model made of vertices and indexed edges. For every frame, I scale a point, rotate it around X, Y and Z,
translate it, subtract the camera position and project it. Perspective divides by depth; orthographic uses
a constant scale. Before projection, an edge crossing the near plane is clipped with linear interpolation.
The Learning Laboratory exposes these exact stages for a selected vertex, compares both projections,
inspects mesh topology, teaches fourteen lessons, tests the student with ten questions and provides a
guided demo. The final UI makes each feature clickable, and the screen-fit layer keeps it usable on
smaller displays. I verified the final source with 86 automated tests, compileall, pip check and static QA
frames.
